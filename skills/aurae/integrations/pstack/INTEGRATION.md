# AURAE with pstack

Read only after selection through the [integration index](../index.md), or before a direct pstack workflow under an installed project instruction block. This module covers pstack's individual skills and `poteto-mode` (sometimes called “potato” by users). It is an optional, portable composition contract, not a pstack installer or an additional lifecycle. Do not modify pstack itself.

## Discover locally, without activating

The index performs the initial lightweight detection without loading this module. Once selected, verify the local pstack identity and task-relevant capabilities before use or project configuration. Reuse unchanged observations; do not scan before every task or message.

- Prefer host-reported identity, scope and location. If necessary, inspect metadata at a host-documented or explicitly supplied local installation location. Do not recursively search a home directory, guess vendor cache paths, contact a registry or execute a plugin to discover it.
- Distinguish **available here**, **not exposed by this host**, and **unknown/inaccessible**. A mention in project memory, a command name or a folder alone does not prove that this session can use it. Never infer absence on other machines from a local check.
- Availability is not activation, approval or compatibility. Respect host trust and invocation policy. Discovery must not install/update pstack, edit global settings, enable poteto or enable AURAE Auto. Before actual use, inspect the selected approved pstack instructions and any applicable adapter; qualify the capabilities required for this task rather than trusting a version number.
- Keep package locations, locally observed versions, tool/model mappings and guard availability in session context or ignored `.scratchpad/aurae/compatibility/` if useful. This cache is disposable and never proof of consent. A shared project preference is not proof of local availability or approval.

If discovery is inconclusive or pstack is unavailable, continue ordinary AURAE work that does not depend on it. Mention the limitation only when it affects the requested outcome. Do not install a replacement, claim pstack ran, or turn missing optional tooling into a project-wide blocker.

## Compose the two workflows

Honor the host's instruction hierarchy and the user's actual scope throughout. In this composition, AURAE owns intent, cycle state, gates, risk, interviews, assurance decisions, project memory and user-facing presentation. pstack supplies execution techniques inside those boundaries, not an alternative source of authorization or lifecycle state. Reuse compatible techniques instead of duplicating plans and reports. If an actual conflict cannot be reconciled within these contracts, hold only the affected action and explain the needed choice; never silently select the weaker safeguard.

| User's request | Interaction and execution |
|---|---|
| Use an individual pstack skill | Use that technique where it fits the current phase; keep ordinary AURAE interaction unless valid Auto scope already applies. |
| Use poteto | Let poteto organize the technical work inside the cycle; its name alone does not delegate AURAE's product choices or activate Auto. |
| Work autonomously with pstack/poteto | Apply [Auto mode](../../references/autonomous-mode.md) within the explicit scope and question policy, together with the selected pstack workflow. Both may be active at once. |
| Resume previously delegated work | Reuse only still-applicable recorded scope and decisions; recheck local capabilities. A plugin's autonomous default, shared preference or session pickup is not a new delegation. |

The presence or invocation of pstack/poteto alone does not activate AURAE Auto, expand its scope or grant merge/publication permission; conversely, AURAE Auto does not automatically enable poteto. Preserve the first-visible welcome for Bootstrap/Adoption, the internal or human interview, and persisted phase views before phase work. Use AURAE's concise voice and question formatting; pstack's principle lists, throughput notes, copied playbook steps and first/final-message templates must not replace the welcome or overwhelm the user. Keep useful execution detail local, with material decisions and evidence in their normal durable locations. Do not mirror every pstack step into a new cycle or Workstream.

- **Assess / Understand:** use read-only investigation, design exploration and bounded disposable experiments to resolve observable uncertainties. Experiments remain within the visible phase and authorized scope; they do not replace questions about user intent, protected choices or permission. Do not change product behavior before Realize or disguise implementation as a prototype.
- **Realize:** use pstack for scoped implementation, host checks and coordination. Frame genuinely independent contributions as concurrent cycles; use optional Workstreams only for inseparable lanes. Respect overlap and integration rules; multiple PRs do not automatically mean multiple cycles.
- **Assure:** resolve participation and required independence under [assurance-participation.md](../../references/assurance-participation.md). Final independent agents verify the stable integrated delivery, not its separate unfinished branches. Branch checks remain host Builder checks; design helpers and repository-mandated reviews are not a substitute for final assurance. Verifiers report, not repair; the host routes findings and rework under [verification discipline](../../references/oracles-capabilities-and-assurance.md#independent-agent-verification-discipline). Preserve pending human feedback and the repeated-serious-failure history.

pstack's shipping, autopilot, “always open a PR”, external updates or skill-repair steps do not grant authority. Confirm the actual source/destination before product integration unless explicit applicable user permission already exists, including when an autopilot label suggests merging. PR creation, push, release, deployment, external messages, global setup and changing another skill require their own applicable authorization. Reuse permissions genuinely supplied in the user's request; do not ask for routine covered work again. An isolated integration candidate is not a landing authorization. Follow [integration](../../references/collaborative-workstreams-and-git-reconciliation.md#integrate-and-close-safely) and [closure cleanup](../../references/project-layout.md#cleanup-at-cycle-closure), never automatic forced worktree removal or a repository-wide cleanup sweep.

Under Auto `none`, an indispensable missing approval becomes a resumable blocker statement, not a question, a fabricated default or an infinite retry. AURAE pause/resume remains the checkpoint owner; local pstack todos/transcripts are supplementary, never the only durable handoff. A normal explanation or investigation still authorizes no implementation, bootstrap or project writes.

## Delegate with the same boundaries

The host agent remains responsible for the cycle. Do not assume that a child inherits either skill, the latest user instruction, or the parent's permissions. Before each dispatch, provide a compact task-specific brief containing:

- a [readable task name](../../references/collaborative-workstreams-and-git-reconciliation.md#name-lanes-and-subagents), intended outcome, cycle/phase and accepted specification or exact candidate reference as applicable;
- the allowed repositories/files, read-only or Builder/Verifier role, writable scratch location and exclusions;
- applicable Auto scope/question policy and actual authorizations or pending decisions, without turning “autonomous” into a blanket grant;
- explicit boundaries relevant to the task: no product changes before Realize, no unilateral gate/expectation changes, no unapproved publication/integration/cleanup, and report-only product findings for verifiers;
- accessible pointers to this addon and the required AURAE owners, plus the selected pstack skill/adapter when used; read them before the corresponding work;
- expected observations/evidence, actual checks and candidate binding, and the instruction to return blockers to the host rather than expand scope or question the user independently.

If the delegate cannot read the approved references, provide the necessary approved contract content through the supported briefing mechanism; do not dispatch without a usable brief or invent shared paths. Carry these constraints into nested delegation too, whenever the host permits it. Stop or narrow running delegation when the user's scope changes; preserve results and do not restart an agent just to change its name.

On return, inspect the actual changes and observations, including unexpected product writes by a supposedly read-only delegate. Verify the authorized scope, candidate, test validity and unresolved findings before accepting its result. A “done” message or pstack verdict cannot advance AURAE's gate by itself. If a boundary was violated, stop the affected continuation, preserve evidence and report the impact; do not conceal it or automatically undo user work.

## Portable capability mapping and protection limits

Use the actual tools, skill invocation policy, permission model and documentation exposed by the host. Map delegation, task tracking, questioning, isolation and reporting by capability rather than hard-coded Cursor, Claude or Codex names. Use a supplied pstack adapter only when applicable and supported; never pass unsupported tool fields, assume a model exists, or use an adapter from another client blindly.

Where no equivalent exists, perform safely serializable Builder work in the host, use a concise Markdown task view if needed, or report the specific unavailable capability. Do not silently drop a required check or represent self-review as independent verification. Missing independence blocks that assurance claim, not unrelated work; use the existing participation/risk rules to resolve the required verifier.

Three layers support the integration:

1. **Portable instructions:** this addon and the project pointer, usable without hooks or a particular client.
2. **Host supervision:** bounded delegation, narrow permissions where available, inspection of actual results and gate checks before consequential actions.
3. **Optional native enforcement:** when the environment provides suitable permissions, sandboxing or hooks, use already authorized controls to constrain sensitive operations and propagate context. Installing or changing controls requires the appropriate approval and validation; this addon does not install hooks or modify global settings automatically.

Markdown is not a technical security boundary. A hook or shell-command pattern alone is not proof that alternative tools or scripts cannot bypass it. Never claim universal enforcement, identical capabilities across clients, or a tested live integration merely from reading these instructions. Qualify only the host/version/capabilities actually exercised. When enforcement is insufficient for a particular risk, keep that action supervised or blocked rather than silently weakening the requirement.
