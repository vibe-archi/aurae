# Interviews and human participation

Read before a discovery interview or any clarification, including internal Auto interviews. For protected authority and gate decisions also read [lifecycle-and-interaction.md](lifecycle-and-interaction.md); for rendering read [status-views-and-voice.md](status-views-and-voice.md).

## Communication contract

Use progressive disclosure in conversation as well as in methodology loading.

By default, communicate only:

- the current objective or outcome;
- the most important risk or blocker;
- the decision needed from the user, if any;
- the next action.

Do not narrate every tool call, Git command, schema field, or internal check. Provide those details only when explicitly requested or needed to explain material risk.

Keep status messages compact. Prefer a short paragraph or at most a few bullets. Do not manufacture completion percentages. Report the AURA's global status, current phase, and phase state separately when that distinction matters.

### Cognitive-load and human-understanding objectives

Reducing the user's cognitive load is an AURAE operating objective throughout specification and development, not merely a conversational preference. The agent should:

- preserve and reuse confirmed context so the user does not repeat earlier answers;
- inspect code, tests, documentation, Git history, and existing AURAE memory before asking for facts it can establish safely;
- separate decisions that genuinely need human judgment from technical coordination the agent can perform within the authorized task;
- propose concise choices or a justified default when they make a decision easier without narrowing intent;
- summarize outcomes, material risks, and the next action instead of exposing routine implementation mechanics;
- maintain resumable state so a user or another contributor does not have to reconstruct the process from conversation history.
- keep human judgment at the center of important decisions and explain outcomes, structure, and behavior clearly enough that the user can understand the project and how its code works, even when some or all of that code is generated by AI.

Efficiency must not hide risk, manufacture consent, combine protected decisions, or reduce required evidence.

## Intent-led participation and handoff

Guide the interaction from what the user wants to achieve, not from a guessed role. Invite the user to describe the desired outcome in their own words. Do not require them to identify as a developer, product owner, project owner, or another profile before helping them.

Adapt naturally to the depth of their answers:

- remain focused on observable behavior, examples, and acceptance outcomes when the user stays high-level;
- explore interfaces, constraints, technical risks, Oracles, and capabilities when the user supplies technical detail or the risk requires it;
- ask about decision authority only when accepting intent, material risk, or another protected decision genuinely requires it.

When the user says the specification is satisfactory:

1. Summarize the confirmed intent briefly.
2. Distinguish a user-confirmed behavioral specification from a fully ready Understand gate. State any remaining engineering risks, Oracles, constraints, or Capability Readiness work.
3. Ask one question offering two paths: continue toward the next phase, or preserve the current state for handoff.
4. If handoff is chosen, persist a compact resume checkpoint containing confirmed intent, the selected AURA and phase (or the ongoing Bootstrap/Adoption interview before any cycle), actual gate readiness, existing accepted baseline references, open risks and questions, required capabilities and their readiness, available exact code references, and the next action. Use [pause-and-resume.md](pause-and-resume.md); do not invent a cycle or baseline for an entry interview.

Do not claim that an incomplete gate has passed merely because the user is satisfied with the behavioral specification. Do not require the next person to recover the previous chat; canonical AURAE memory must contain the durable context. When handoff is expected through a cloned repository, follow [git-storage-and-sync.md](git-storage-and-sync.md#handoff-through-a-clone).

## Adaptive low-load interview protocol

Apply this protocol during Bootstrap, Adoption, Understand, and any later clarification unless an explicitly requested Auto mode is active. In Auto mode, follow [autonomous-mode.md](autonomous-mode.md): keep the same discovery topics and question analysis, but resolve the queue internally from evidence and justified recommendations. Suppress only avoidable user-facing questions and queue announcements. Use this protocol for any question that remains genuinely necessary and permitted by the selected question policy.

### Queue visibility and numbering

When a bounded interview has an identifiable queue of main questions:

1. Before the first question, state briefly why the interview is needed and announce the current number of main questions.
2. Explain that AURAE will group only simple questions, revisit every discussion item individually, and let the user request one-at-a-time presentation at any moment.
3. Number each main question as `Q<n> / <total>` without an `AURAE :` prefix.
4. When an answer requires clarification, keep the follow-up under its parent: `Q3.1 / 10`, then `Q3.2 / 10`, and so on. Use deeper nesting such as `Q3.1.1 / 10` only when it genuinely improves traceability.
5. After a batch, process all answers, then revisit `discuss` items one at a time in their original order before presenting another batch or leaving the topic. Follow-ups do not increase the main-question total.
6. If new information adds or removes main questions, announce the revised total before continuing. Never silently renumber a question already shown to the user.
7. Announce the queue once at the start, then only when its total changes or when resuming an interrupted interview.

Use the user's language and adapt the purpose statement. For example:

```text
✨AURAE ~ Afin d'établir la base de travail, j'ai identifié 10 questions principales.
Je regrouperai seulement les questions très simples. Les autres seront posées une par une, et tu peux me demander le mode une par une à tout moment.

Q1 / 10
Quel résultat veux-tu obtenir en priorité ?
```

This numbering is required for questions belonging to an announced interview queue. An isolated question outside such a queue does not need an artificial `Q1 / 1`.

### Question presentation and recommendations

Use the complete portable/native rendering contract in [status-views-and-voice.md](status-views-and-voice.md#questions-and-recommendations).

Evaluate each question independently for a recommendation. Base a recommendation on repository evidence, accepted intent, risk reduction, established project conventions, reversibility, or a clearly simpler safe default. For a batch, provide a recommendation for every item where such a basis exists; do not replace them with one recommendation for the whole batch.

Do not manufacture a preference for factual discovery, personal preference, authority or identity confirmation, or a question whose answer is not supported by evidence. A protected decision may receive an evidence-based recommendation, but the recommendation must remain visibly advisory and the authorized person must still choose explicitly. The user may always disagree, answer in their own words, or request discussion.

### Batching simple questions

Batching is a low-effort triage mechanism, not a shortcut around discussion or consent.

For yes/no questions:

1. Group three or four only when each question is simple, independent, and understandable without switching context or reading technical detail. Do not delay the interview or invent filler questions merely to reach the batch size.
2. Label every item with its normal `Q<n> / <total>` identifier.
3. Add an individual `Recommendation` line to every item for which AURAE has a justified preference.
4. Tell the user they may answer `yes`, `no`, or `discuss` for each number, using equivalent words in the user's language. Accept a clear free-form answer; do not require rigid syntax.
5. Treat `discuss` as unresolved, never as consent or rejection. Reformulate it as `Q<n>.1 / <total>` and explore it individually. If several items are marked for discussion, handle them one at a time in their original order.

For simple multiple-choice questions:

1. Group two or three only when they concern closely related subjects, remain independent, and each has a short set of obvious, unambiguous options.
2. Keep option labels local to each numbered question and add an individual recommendation when justified.
3. Tell the user they may select an option, answer in their own words, or request discussion.
4. Requeue a discussion request under its original question number and handle it one at a time.

Never batch an open-ended or ambiguous question, a question whose answer changes the meaning of another, a protected decision, material-risk acceptance, permission for an external or hard-to-reverse action, or any question that needs explanation before the user can answer responsibly. Respect a user's request to receive everything one at a time.

A suitable yes/no batch is:

```markdown
Q2 / 10

**Le produit doit-il fonctionner hors connexion ?**

💡 **Recommandation : Non** — aucun usage hors connexion n'a été identifié pour le moment.

Q3 / 10

**Faut-il conserver les données après la déconnexion ?**

💡 **Recommandation : Oui** — cela évite une perte de travail involontaire.

Q4 / 10

**Une exportation des données est-elle nécessaire ?**

> Pour chaque numéro : **Oui**, **Non** ou **Discuter**.
> Exemple : Q2 non, Q3 discuter, Q4 oui.
```

If the user answers `Q3 discuter`, continue with one question:

```markdown
Q3.1 / 10

**Quelles données souhaites-tu conserver après la déconnexion ?**
```

### Interview flow

1. Use already available project evidence and confirmed answers before adding a question to the queue.
2. Select the next unanswered topic and decide whether it qualifies for a simple batch. Otherwise ask only its single most useful question.
3. When one question has a small set of obvious, meaningfully distinct answers, offer a concise list, usually two to four choices. State that the user may select one, request discussion, or answer in their own words.
4. Evaluate that question for a recommendation. Put a recommended choice first when evidence, safety, or confirmed intent makes one option preferable, then add the standard `Recommendation` line with at most one brief reason. Never preselect a protected decision.
5. Keep a question open when choices would be invented, misleading, incomplete, or would narrow discovery too early.
6. Ask in plain language, using either one question or one eligible batch. Do not append unrelated questions.
7. Wait for the user's answer and process every item before selecting the next question or batch.
8. Record each answer, its source, and whether it is confirmed or inferred. Keep every discussion item unresolved until its individual follow-up is answered.
9. Periodically rephrase the current understanding and ask for confirmation as one question.
10. Stop interviewing when the current commitment is sufficiently understood for its risk.

Let the user's intent and accumulated answers determine the next question. Do not insert role-discovery questions unless authority or provenance is material to the decision at hand.

During an explicit `/AURAE pause`, follow [pause-and-resume.md](pause-and-resume.md) and save that queue, actual questions/choices, received answers and their source/status, unresolved follow-ups and the next item in its durable cycle or pre-cycle entry resume point. Do not wait until the interview is complete or claim a durable save from chat/scratch alone. If Git storage is not yet usable, only the explicitly limited provisional export in that contract is available. On `/AURAE resume`, reuse the exact labels and later confirmed progress; Q4 asked without an answer is not the same as Q4 answered with Q4.1 still unresolved. This explicit checkpoint does not impose per-answer Git commits during ordinary questioning.

Maintain a private queue if helpful. Preserve enough numbering state to resume without restarting or changing already visible labels:

```yaml
interview:
  purpose: establish_expected_behavior
  main_total: 10
  current_main: 3
questions:
  - id: Q3.1
    parent: Q3
    topic: expected_behavior
    status: planned | asked | answered | validated | deferred
    answer_source: user | repository | inference
```

Do not store speculative questions as canonical project facts. A requested resume point may preserve them as explicitly provisional workflow context; this records what remains to discuss, not approved intent. Promote only validated outcomes into specifications, risks, decisions, or assumptions.
