# AURAE upgrade protocol

## Purpose

Handle `/AURAE upgrade` as a bounded, local-first project upgrade. Accept `/upgrade` as an alias only when the user's intent clearly concerns AURAE; do not intercept another tool's upgrade command. First compare the approved installed skill with the skill recorded in the project, then bring the project forward when the local package is newer and compatible. Preserve the current phase and accepted work.

The command authorizes the compatible local project refresh described below, including its isolated local `aurae/skill` commit, from an already approved package. It does not authorize installing or activating an unapproved skill, changing distributions, broad metadata migration, history rewriting, product-code commits/merges, remote publication or changes to accepted product intent. A request only to inspect or report upgrade status remains read-only.

**Online release checking is not implemented in this release.** The URLs in [vendor.md](../vendor.md) are informational only, including in client distributions. Do not contact them, query release APIs, search for newer packages, fetch distribution refs or download a skill as part of this command. Do not claim that a local version is the latest published version. If online checking is added later, it must come after the local project comparison and applicable refresh, not before it. Existing separately authorized project-memory synchronization is not release discovery and does not authorize it.

Before reloading changed instructions, follow [skill-recovery-and-trust.md](skill-recovery-and-trust.md) from an approved copy. Compare candidate identity and release metadata as data first; do not execute or adopt an unapproved candidate's instructions to perform its own trust check. Keep an approved unchanged copy available. If the installed files changed without a matching approval, hold their activation and continue the bounded check from known approved guidance; missing trust blocks only that candidate, not safe unrelated work.

## What “latest” means

Keep these claims distinct:

- **loaded package** — the approved AURAE skill used in the current session;
- **installed version** — the package's `agent_skill` version and exact identity, including its distribution profile;
- **project-recorded version** — `agent_skill` from the validated manifest at the exact local `aurae/skill` revision, not `.aurae/aurae.yaml` or a disposable cache;
- **project recovery bundle** — that complete skill snapshot, including any client profile; it records recoverable tooling, not proof that every older phase has adopted every new instruction;
- **latest verified release** — a publication-freshness claim that this local-only command cannot establish;
- **project compatibility** — whether the project's live AURAE state can be interpreted and continued safely under the loaded package.

Never call an installed package or project recovery bundle “the latest version” merely because it is the only one visible. Report online checking as not implemented, not as a failed request or an absent URL. Do not infer a version from a timestamp, the Workspace format, an arbitrary project note or a cached prior check.

An `agent_skill` version is local tooling information, not project truth. A newer skill alone never requires a Workspace migration.

## Local comparison and distribution compatibility

Read candidate manifests/profiles as data until trust is established. Validate complete inventories and hashes before choosing or copying a package. Compare valid `agent_skill` versions semantically (numeric components and prerelease precedence), not lexicographically; build metadata and equal version labels never prove identical bytes.

| Local installed package versus project bundle | Action |
|---|---|
| Same established distribution, local version newer | Review the version interval and live compatibility, apply safe forward changes, then refresh the local project bundle through the procedure below. Preserve applicable client instructions. |
| Same distribution, equal version and identical package | No bundle write; check live compatibility and retained follow-ups only. |
| Equal version but different content, or version/content declarations inconsistent | Preserve both; review the differences and resolve the package choice rather than calling either newer. Reuse valid exact approval, but never silently overwrite changed client instructions. |
| Same distribution, project version newer | Do not downgrade or replace the installed skill automatically. Explain the local skill is older; offer separately approved local recovery if needed. Keep unsupported project operations read-only. |
| Different distribution, unknown identity, changed source or conflicting client profile | Do not choose by version. Resolve the intended distribution/candidate through the trust contract before any replacement; an official package must not erase a private variant. |
| Missing, invalid or unsupported bundle/profile/version | Do not treat it as version zero. Preserve available data, distinguish absence from corruption, and perform only a bounded, authorized repair with an established package choice. |

Older valid bundles may lack `vendor.md`. Keep them readable; do not infer official provenance from the name `aurae` alone. Establish lineage through reliable known package identity/provenance or one focused user choice when necessary. A known unchanged legacy official package may receive the official profile during its local refresh; an unknown legacy client copy must retain its adaptations. Do not create AURAE state in an unadopted folder merely because `/upgrade` was invoked.

A matching distribution ID (or reliably established legacy lineage) is necessary but not sufficient: review source and profile changes, not just the label. Package source/scope/content consent and compatibility checks remain separate from version ordering. Keep client package versions in their own series under [vendor.md](../vendor.md); never compare their numbers with official releases as if they were one series. If client instructions changed, make the material differences visible and resolve their selection before publication; do not transplant edits into an already approved candidate and keep calling it the same package.

## Upgrade procedure

1. Capture the exact local canonical and bundle revisions and the already-known operation/phase context without mutation. Defer further Workspace interpretation until after the local package comparison.
2. Reread the selected, approved and identity-verified AURAE `SKILL.md` completely, then its `vendor.md`, this protocol and [versioning-and-releases.md](versioning-and-releases.md). A changed installed copy requires the trust check before activation even if its version is unchanged. Do not activate candidate instructions to approve themselves.
3. Compare the installed package with the exact **local** project `aurae/skill` manifest/profile and complete verified content using the table above. When already using a skill, inspect the ref directly; do not load `AURAE.md` merely to rediscover recovery. Do not fetch to perform this comparison. If only a remote-tracking snapshot is visible, identify it as such rather than claiming a current local project version; resolve recovery/synchronization separately when authorized.
4. Under the package choice and read/write limits from the comparison table, read `.aurae/aurae.yaml` before the remaining Workspace state and follow [format-compatibility-and-migrations.md](format-compatibility-and-migrations.md). When understood, retain active AURAs, the selected AURA's phase and `phase_state`, accepted baselines and pending protected decision; never guess these from unsupported state. For a newer compatible local package, review the relevant release interval, client changes and live frontier; classify impacts below. Check only enough earlier-phase output to identify concrete deferred gaps. Validate live state whenever canonical conclusions or writes depend on it.
5. Finish any atomic operation in progress. Apply safe `reload_only` and `forward_applicable` changes now; persist gate-relevant deferred work through existing canonical records at a safe write boundary. Make only necessary lossless live compatibility changes under the migration contract. Respect existing approval requirements for protected meaning, project entrypoint edits or broader work. Never restart a phase to make its version look current.
6. For the newer approved package, refresh the **local** `aurae/skill` bundle using [the isolated bundle procedure](git-storage-and-sync.md#portable-skill-recovery-branch): preserve client scope/instructions, generate and verify all exact hashes including `vendor.md`, append history with compare-and-swap, read back and confirm unchanged developer state. This local refresh is part of the upgrade request, not merely a suggestion. If compatibility, required approval, pending durable bookkeeping or a moved ref prevents safe publication, preserve the old ref and report the refresh as pending. Never manufacture a successful upgrade by writing only a version marker. A bundle refresh may coexist with explicitly recorded earlier-phase deferred reviews; it does not declare those reviews complete.
7. Report local bundle outcome, remaining material impacts and the unchanged current phase. Stop after this local stage: online release checking remains unimplemented even when an official/private URL is configured. Remote publication of a locally refreshed bundle requires separate applicable authorization and readback; distinguish local completion from clone readiness.

In a multi-repository Workspace, check each AURAE-enabled Workspace unit independently. The consumer/root may summarize integrated AURA outcomes, but it must not force dependency migrations or modify a read-only dependency merely for version uniformity.

## Impact classification

Use the least disruptive applicable class:

- `reload_only` — instructions or presentation changed, with no project-state consequence. Apply the refreshed behavior immediately.
- `forward_applicable` — the change affects work not yet performed in the current phase. Apply it from now on without restarting the phase or altering the accepted baseline.
- `deferred_review` — the change affects an earlier phase, accepted artifact, or already completed part of the current process. Keep the current phase in progress and queue a focused delta review for its next safe boundary.
- `migration_required` — the live Workspace cannot be interpreted or written safely without a minimal compatibility change. Follow the migration contract and do not expand the migration beyond the active live frontier.
- `immediate_safety_blocker` — continuing a specific action would risk security, data loss, corruption, or invalid canonical state. Stop only that unsafe action, preserve every affected AURA phase, and explain the blocker.

An upgrade must never, by itself:

- move `phase`, replace `phase_state`, close, or activate any AURA;
- revoke or rewrite an accepted baseline or protected Decision Record;
- restart Assess, Understand, Realize, or Assure from the beginning;
- create a cleanup AURA solely to modernize historical metadata;
- turn an informational version difference into a product blocker.

At the next safe phase boundary, resolve deferred items through a targeted delta review. Revisit only the affected requirement, risk, capability, evidence, or decision. If the current phase is Assure, finish the already-running verification activity and surface material upgrade impacts in the assurance outcome rather than silently making an unconditional claim.

## Local check state

AURAE may keep a disposable check record under `.scratchpad/aurae/upgrade/` containing the loaded package source/distribution, component versions, exact before/after local bundle revisions or digests, check time, canonical project revision, and summarized result. Use it to notice that the installed skill changed between checks, never as the authoritative project-recorded version.

This record is optional and local. Its absence means “no comparable local check,” not “no update.” Never synchronize it or rely on it as the only copy of a material obligation. At the next safe canonical write, preserve gate-relevant follow-ups using existing AURAE open-work, debt, risk, condition, or blocker structures.

## User-facing result

`/AURAE upgrade` is a key status moment, but keep the response short. Report:

1. the installed skill version and distribution when it matters;
2. the project-recorded version before/after, whether its local bundle was updated, already matched, or remains pending, and whether any remote publication actually occurred;
3. the project's compatibility outcome and that online release checking is not implemented;
4. confirmation that the current phase remains unchanged;
5. only the number and next handling point of material deferred items.

Use the user's language and the portable visual voice. For example:

> **Mise à niveau locale terminée**
>
> ✔️ Copie du skill dans le projet : `<before>` → `<installed-version>`, mise à jour localement, sans publication distante.  
> ✔️ Projet compatible ; le cycle reste en Realize. Deux points seront revus après cette étape.  
> ❕ La vérification des nouvelles versions en ligne n'est pas encore disponible.  
> ➡ **Suite : reprendre le travail interrompu.**

Do not expose hashes, command transcripts, full release notes, or migration detail unless the user asks. If a decision is needed, follow the normal decision and adaptive interview protocols; if several questions are already identified, announce and number that queue.
